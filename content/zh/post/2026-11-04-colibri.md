# colibri 评测：47k Star 的纯 C 推理引擎，让 744B 大模型在 25GB 内存的笔记本上跑起来

你手上有一台 32GB 内存、单张 RTX 3060 的机器，想跑 300B 以上的模型。llama.cpp 会告诉你放不下，Ollama 会直接开始 swap 然后卡死，vLLM 会告诉你需要 4 张 H100。

**colibri** 给出的答案是：既然 Mixture-of-Experts 模型每个 token 只激活 5% 左右的参数，那模型就不需要「装进」内存，它只需要被「安排好」。

一句话简介：**colibri 是一个纯 C 写的分层 MoE 推理引擎——把专家分成显存、内存、NVMe 三级，按实际路由热度自动搬运，让前沿大模型跑在你已有的硬件上。**

- **GitHub**：https://github.com/JustVugg/colibri
- **官网**：https://justvugg.github.io/colibri
- **协议**：Apache 2.0
- **画像**：Star 47,382 / Fork 5,471 / 创建于 2026-07-01 / 最新版 v2.1.0（2026-10-31）
- **技术栈**：纯 C，无 BLAS、运行时无 Python；Python 只负责安装器、启动器和 API 网关
- **语言**：README 提供简中、繁中、日、意、印尼、葡语等 8 种版本

## 核心功能

### 1. 专家的三级驻扎：VRAM / RAM / NVMe

这是 colibri 的全部意义所在。以 GLM-5.2 为例：744B 参数，每个 token 只用 40B，其中真正在 token 之间变化的「路由专家」只有约 11GB。

于是模型被这么切开：

| 层 | 放什么 | 特点 |
| --- | --- | --- |
| **GPU（VRAM）** | 最热的专家 + dense 层 | 最快，但容量最小 |
| **RAM** | dense 部分（attention、共享专家、embedding）+ 温专家 | 中等速度，几十 GB 量级 |
| **NVMe 磁盘** | 冷专家，按需 `pread` 读入 | 慢，但容量几乎无上限 |

关键设计承诺是：**放置位置只影响速度，不改变模型的精度和路由语义**。一个专家从显存还是从磁盘回答，路由器看到的权重是同一位元的。这一点在作者的设计里被反复强调，也是它能被当作「研究平台」而不是「玩具」的前提。

### 2. 一个「权重版 JIT」：用得越久越快

colibri 用 JIT 编译器的比喻来解释它的缓存策略：JIT 不会编译整个程序，它观察哪些路径热、只编译热路径。colibri 观察的是路由：

- 每层一个 LRU 缓存；
- 外加一份从你自己的对话里学出来的 pinned hot set（`.coli_usage`，每轮更新）；
- 下一层的路由有 71.6% 可在前一层预测，于是有一个 lookahead 线程做预取。

换句话说，你用它写代码写了一周，它就会把写代码时反复激活的那批专家钉在显存里。**这不是玄学，是可测量的路由结构**——仓库里有一张「专家图谱」（expert atlas）议题专门收集这类数据。

### 3. 不被磁盘拖两次：`pread` / loader 池 / 批量去重

流式推理最怕的是「每个 token 都等一次磁盘」。colibri 做了几件事：

- 一个专家的三个矩阵用**一次** `pread` 读完；
- 一组 loader 线程在常驻专家计算的同时，把缺失的读进来；
- 一个 batch 里的多个位置共享同一次专家读取；
- `DIRECT=1`（O_DIRECT）在好的 NVMe 上收益明显，在差的盘上可能负收益——文档要求你自己测。

### 4. 多盘与多机：把独立带宽变成解码速度

```bash
COLI_MODEL_MIRROR=/second/glm52_i4 ./coli chat --model /fast/glm52_i4
```

两块独立控制器的 NVMe 实测解码 **+37.5%**。还有一个 cluster 模式，可以把路由专家分到别的机器上跑。这一层设计让 colibri 从「笔记本玩具」一路能延伸到「小机架」。

### 5. OpenAI / Anthropic 双兼容 + 完整可视化面板

`coli serve` 起一个本地服务，同时提供：

- **OpenAI 兼容**：`/v1/chat/completions`、`/v1/completions`、`/v1/models`，支持流式、JSON、stop、logprobs；
- **Anthropic 兼容**：`/v1/messages`，所以 **Claude Code 和 Anthropic 官方 SDK 可以直接连**；
- **工具调用**：除 Inkling 和 OLMoE 外所有对话引擎都支持；
- **图片输入**、**文档输入**（`/file PATH`，支持 PDF）、**Qwen-Image-2.1 出图**；
- **`--kv-slots N`**：最多 16 个并发会话，各自独立 KV cache，一起解码。

面板部分包括 chat UI、监控页、**专家热力图**（每个专家一个格子，当前步被选中变白、本次回答用过变琥珀色）、Profiling 页（逐阶段耗时，最近 30 轮趋势）。

最后这个「专家地图」其实是 colibri 最有趣的地方——**它把 MoE 的黑箱拆开给你看**。`llama.cpp` 不会告诉你哪个专家在工作，colibri 会。

### 6. System One：不生成 token，只给概率

一个容易被忽略但很实用的模式：给它一份文档和一组允许的答案，它直接读取每个选项的概率，一次前向出结果，**零 token 生成**。

README 里的例子：Qwen3.6-35B 在 RTX PRO 4000 上读一个「破坏缓存大小上限」的 PR，输出 *request changes 81%，熵 0.56*。这类分类 / 审核 / 路由任务，用它比让模型写一段话再解析快一个数量级。同一份文档问四个问题，只读一次，实测比重跑四遍快 5.7 倍。

## 支持哪些模型

13 个引擎，以「一族一个 C 文件」的方式实现：

**常驻内存的小模型**

| 模型 | 下载 | RAM |
| --- | --- | --- |
| Qwen3.6-35B-A3B | 23 GB | 10 / 20 GB |
| Qwen3-Coder-30B-A3B | 19 GB | 8 / 18 GB |
| Qwen-Image-2.1 | 33 GB | 12 / 18 GB |

**流式读取磁盘的大模型**

| 模型 | 下载 | RAM |
| --- | --- | --- |
| DeepSeek V4 Flash（284B） | 167 GB | 16 / 32 GB |
| MiMo-V2.6 Flash（309B） | 172 GB | 32 / 52 GB |
| Qwen3.8-Flash-Next（125B） | 186 GB | 24 / 32 GB |
| GLM-5.2 / 5.3（744B） | 429 / 419 GB | 16 / 24 GB |
| Inkling（975B） | 514 GB | 120 / 128 GB |
| Kimi K3（2.8T） | 1.56 TB | 32 / 64 GB |

另外支持直接读已发布的 GGUF（`coli import`），从 IQ1_S 到 Q8_0、F16、BF16、MXFP4 全部支持，不重新量化——Mistral-Large-4、Muse Spark Open、Flint、LFM3-VL 就是这么跑的。

三个专用的「决策模型」（Laya、GLiNER2.5-Decide、Clef）也原生支持，带作者原本标定好的校准参数。

## 实测速度：需要先降低期望

这部分必须说清楚，因为 README 自己就是诚实的。

**GLM-5.2（744B）解码速度阶梯：**

| 硬件 | tok/s |
| --- | --- |
| 6× RTX 5090，全部常驻 | 9.0–9.2 |
| 128GB，纯 CPU（Ryzen AI Max+ 395） | 1.83 |
| 单张 RTX 5070 Ti 笔记本级 | 1.07 |
| 25GB 笔记本，冷启动 | 0.05–0.1 |

**一台 i5-13500 + 62GB RAM + RTX PRO 4000（24GB）的三后端对比**（450 token prompt，128 token 回答）：

| 模型 | CUDA 解码 | Vulkan 解码 | CPU 解码 |
| --- | ---: | ---: | ---: |
| Qwen3.6-35B-A3B Q4_K_M | 104.8 | 92.9 | 13.9 |
| LFM3-VL-2B Q4_K_M | 235.1 | 214.1 | 34.5 |
| OLMoE-1B-7B Q4_K_M | 354.6 | 299.4 | 47.4 |

**大模型从 GGUF 流式读取**（同一台机器，两块 NVMe）：

| 模型 | 大小 | 解码 tok/s |
| --- | ---: | ---: |
| Inkling-Small UD-IQ2_XXS | 77 GB | 10.9–11.5 |
| MiMo-V2.6-Flash Q2_K_S | 106 GB | 7.8 |
| DeepSeek V4 Flash UD-IQ2_XXS | 85 GB | 6.2 |
| Muse Spark Open UD-IQ1_S | 176 GB | 1.55–1.58 |
| GLM-5.2 UD-IQ1_S | 202 GB | 0.63–0.66 |
| Kimi K3 UD-IQ1_S | 594 GB | 0.35 |

**结论很明确：** 小模型（35B 以下）在这套引擎上速度是够用的，GPU 上一百 tok/s 属于日常可用。但**几百 B 的巨兽是「能跑」而不是「好用」**——0.6 tok/s 意味着等一句话要几分钟。作者自己在 README 里把 25GB 笔记本的 0.05 tok/s 称为「the honest floor」（诚实的底线），这个态度值一个赞。

长上下文方面有个亮点：Qwen3.8-Flash-Next 在 262,144 上下文下，prompt 从 15.6 提到 149 tok/s，解码从 9.6 提到 45.7——256k 上下文的实际手感接近 64k。

## 适合谁用

**适合：**

- **硬件受限的本地部署玩家**。有 32–64GB 内存 + 一块消费级显卡，想摸一摸 300B 级别的模型到底什么水平。
- **想研究 MoE 路由的人**。专家热力图、Profiling 页、可复现的 benchmark 协议，这些在别的引擎里没有。
- **做分类 / 审核 / 路由的工程师**。System One 的「一次前向给概率」模式，比让 LLM 生成再解析便宜太多。
- **多机 / 多盘折腾党**。镜像读、cluster 模式，这些玩法别的项目基本不提供。

**不适合：**

- **要生产级吞吐的团队**。vLLM、SGLang 的 continuous batching 和 PagedAttention 仍然是这场景的正解。
- **只想「装个 Ollama 聊聊天」的用户**。colibri 的一步安装不算难（`./start-here.sh` 一次搞定），但它会问你选哪个模型、下载几十上百 GB，心智负担比 `ollama run` 重。
- **追求「原生速度」的人**。如果你的模型本来就放得下显存，用 llama.cpp 或直接用 vLLM 更快，不必绕这一圈。

## 与同类工具对比

| 维度 | colibri | llama.cpp | Ollama | vLLM |
| --- | --- | --- | --- | --- |
| **定位** | 超大规模 MoE 的磁盘流式推理 | 通用 GGUF 推理 | 开箱即用的本地模型管理器 | 生产级高吞吐服务 |
| **模型放不下内存时** | 按专家粒度流式读取，**这是它的主场** | mmap 兜底，容易疯狂 swap | 基本放弃 | 不支持 |
| **最大可跑规模** | 2.8T（Kimi K3） | 取决于 mmap，实践上限远低 | 同 llama.cpp | 显存上限 |
| **后端** | CPU / Vulkan / CUDA / Metal | CPU / CUDA / Metal / Vulkan | 同 llama.cpp | CUDA / ROCm |
| **量化支持** | 自有 int4 容器 + 全系 GGUF | GGUF 全家桶 | 同 llama.cpp | GPTQ / AWQ / FP8 |
| **可观测性** | 专家热力图、逐阶段 profiling | 基础日志 | 基础日志 | Prometheus 指标 |
| **API 兼容** | OpenAI + Anthropic + Jev | OpenAI | OpenAI | OpenAI |
| **上手成本** | 中（要选模型、下大文件） | 中（编译 / 参数） | 极低 | 高（要配服务） |
| **典型用户** | 硬件受限的研究者 / 折腾党 | 本地推理主力 | 普通用户 | 推理服务团队 |

一句话分工：**模型装得下 → 用 llama.cpp；要开箱即用 → 用 Ollama；要跑服务 → 用 vLLM；模型装不下但又想跑 → 才轮到 colibri。**

这个定位其实很干净。它不去抢 llama.cpp 的地盘，它做的是 llama.cpp 明确不做的那件事。

## 如何使用

### 方式一：一步安装（推荐）

**Linux（Ubuntu / Debian）：**

```bash
sudo apt install git python3 build-essential
git clone https://github.com/JustVugg/colibri
cd colibri
./start-here.sh
```

**macOS：**

```bash
xcode-select --install
brew install libomp git python
git clone https://github.com/JustVugg/colibri
cd colibri
./start-here.sh
```

**Windows：** 下载 ZIP，双击 `START-HERE.bat`（缺 Python 会自动帮你装）。

脚本会做五件事：

1. 探测机器（RAM、空闲磁盘、CPU、GPU）；
2. 推荐一个装得下的模型（常驻部分 + 最小专家缓存必须进 RAM）；
3. 编译引擎。有编译器就本地编，把 GPU 也编进去；没有就下预编译版。CUDA 装了 CUDA toolkit 就编 CUDA，否则走 Vulkan；
4. 下载模型，**支持断点续传**——断了重跑就接着下；
5. 起服务并打开面板，打印两个关键地址：

```
Browser:             http://127.0.0.1:8000/
OpenAI base URL:     http://127.0.0.1:8000/v1
Anthropic base URL:  http://127.0.0.1:8000
```

**下次启动**只需再跑一次 `./start-here.sh`，不下载不编译，秒进。

常用参数：

| 参数 | 作用 |
| --- | --- |
| `--list` | 列出所有模型，并说明哪个装不下、为什么 |
| `--model ID` | 指定模型，如 `--model qwen36-35b` |
| `--yes` | 不问，直接采用推荐 |
| `--dir DIR` | 模型放别的盘（默认 `~/colibri-models`） |
| `--backend vulkan/cuda/cpu` | 强制指定后端 |
| `--reconfigure` | 重新选模型 |

### 方式二：让 AI 助手帮你装

如果你用 Claude Code / Codex 之类的助手，直接说：

> 按照 https://github.com/JustVugg/colibri 的 docs/AI_SETUP.md 在这台机器上装好 colibri

`AI_SETUP.md` 把每一步写成了「命令 + 机器可读结果」，并规定下载模型、装系统包前必须先问你。支持 MCP 的助手还能直接用 `coli mcp` 提供的工具（探测硬件、推荐模型、安装、启停、检查状态）。

### 方式三：手动（适合想控制每一步的人）

```bash
git clone https://github.com/JustVugg/colibri && cd colibri/c
./setup.sh                 # 检查 gcc/OpenMP，编译，自测
make qwen36 VK=1           # 单独编译一个引擎，VK=1 是 Vulkan，CUDA=1 是 CUDA
```

然后：

```bash
./coli chat   --model /nvme/qwen36      # 终端里聊
./coli web    --model /nvme/qwen36      # API + 面板，自动开浏览器
./coli serve  --model /nvme/qwen36      # API + 面板，不开浏览器
./coli plan   --model /nvme/qwen36      # 预演：模型会放在哪
./coli doctor --model /nvme/qwen36      # 只读体检
./coli tune   --model /nvme/qwen36      # 实测并保存这台机器最快且安全的参数
./coli import /nvme/Flint-UD-Q4_K_XL.gguf   # 导入已有 GGUF
```

`coli plan` 这个命令值得单独夸一句：**跑之前先告诉你权重会怎么分布**，这在动辄下载几百 GB 的场景里能省掉大量试错。

### 接到编辑器 / CLI

任何 OpenAI 兼容的客户端：

- Base URL：`http://127.0.0.1:8000/v1`
- 模型 ID：`coli status` 打印的那个
- API Key：任意非空字符串

Claude Code 走 Anthropic 兼容口，直接把 base URL 指过去即可。

## 几个需要留意的地方

**磁盘不是可选项，是核心部件。** 官方自己说得很直白：「大模型的瓶颈是磁盘」。SATA SSD 上跑 300B 会是灾难，NVMe 是最低要求，两块独立控制器的 NVMe 才有质变。WSL 用户注意：模型目录别放 `/mnt/c`，那会慢好几倍。

**首次使用需要耐心。** 下载几十到几百 GB，第一次跑起来还要做缓存预热。JIT 式的学习缓存意味着**头几轮速度不是终态**，用久了才会快。

**量化格式要选对。** 文档明确警告：GLM-5.2 不要用老的 per-row int4 镜像，质量差约 9 个点，还会导致答案循环（issue #455）。要用 gs64 分组量化的容器。

**项目还年轻。** 2026 年 7 月创建，四个月冲到 47k Star，169 个 open issue。速度惊人，但也意味着 API 可能变、文档可能滞后、遇到坑需要翻 docs 或开 issue。

**它不是「更快的 llama.cpp」。** 如果你的模型完全装得下内存，colibri 不会比 llama.cpp 快，反而多了一层间接。它的价值只在「装不下」这个区间内成立。

## 总结

| 维度 | 评价 |
| --- | --- |
| **创新性** | ★★★★★ 专家级分层放置 + 学习式 pin，思路清晰且可复现 |
| **实用性** | ★★★☆☆ 35B 以下很顺，几百 B 是「能跑」而非「好用」 |
| **工程质量** | ★★★★☆ 纯 C、无运行时依赖、CI 对参考实现做校验、benchmark 协议完善 |
| **文档** | ★★★★☆ docs/ 目录极其详尽，8 种语言 README，缺点是真的太长了 |
| **上手难度** | ★★★☆☆ 一步脚本够傻瓜，但选模型和等下载仍需耐心 |
| **推荐指数** | **★★★★☆（4/5）** |

colibri（蜂鸟）这个名字起得很好：一只几克重的鸟，每天拜访上千朵花。它把 744B 的巨兽维持在一只蜂鸟的口粮上——25GB 内存、12 个 CPU 核，和大量的磁盘耐心。

它不会取代 llama.cpp，也不打算取代 vLLM。它填补的是一个很具体、很多人真实面对的空白：**我有一台不错的机器，但它就是装不下我想跑的那个模型。** 在这件事上，colibri 目前可能是做得最认真的那个。

如果你是本地部署爱好者，值得花一个周末试试。如果你是生产环境的工程师，先收藏，等它再成熟两个版本。
