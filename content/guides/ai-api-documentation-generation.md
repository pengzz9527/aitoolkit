你的产品上线了，用户问"你们的接口怎么调用？"——你翻遍了代码，发现根本没有文档。或者你是产品经理，需要给开发团队写接口规范，但每次改需求都要手动更新文档，改到崩溃。

**2026年，这些工作已经不需要手动完成了。**

AI 可以直接读取你的代码或接口定义，自动提取所有接口信息、参数说明、返回格式，并生成结构化的 API 文档。本文从最实用的场景出发，让你零基础完成一套专业级的 API 文档。

---

## 一、准备阶段：让 AI 看到你的接口

AI 生成 API 文档的第一步，是让它"看到"你的接口信息。根据你的技术栈，有三种最常用的方式。

### 方式 A：如果你有 JSON/YAML 格式的接口定义

很多项目会在 `openapi.json`、`swagger.yaml` 或 `api-spec.json` 中维护接口定义。直接把这些文件上传给 ChatGPT 或 Claude，它们能瞬间理解整个接口体系。

**实操步骤：**

1. 找到你的接口定义文件（通常在项目的 `docs/`、`spec/` 或根目录下）
2. 如果文件很大（超过 50KB），先用 198007.xyz 的 [JSON 格式化工具](/tools/json-formatter/) 检查一下格式是否正确，避免上传后 AI 解析出错
3. 把文件拖进对话框，然后说：

```
我上传了一份 OpenAPI/Swagger 格式的接口定义文件。请帮我做以下事情：
1. 列出所有接口的路径、方法和简要描述
2. 每个接口提取：请求参数（名称、类型、是否必填、说明）、响应格式（字段名、类型、说明）
3. 为每个接口生成一个 cURL 调用示例
4. 最后输出一份完整的 Markdown 格式 API 文档
```

### 方式 B：如果你只有代码，没有接口定义

这是最常见的情况——你的代码写了接口，但没有维护任何文档。这时候可以让 AI 从代码中提取接口信息。

**实操步骤：**

1. 打开你的后端代码目录，找到定义路由和接口的文件（比如 Flask 的 `routes.py`、Express 的 `router.js`、Spring Boot 的 `@RestController` 类）
2. 把相关文件的代码复制粘贴给 AI，一次不要超过 500 行（如果文件太大，按功能模块拆分）
3. 输入指令：

```
以下是我的后端代码中的路由定义。请帮我分析并提取：
1. 所有 HTTP 端点（方法 + 路径）
2. 每个端点的请求体/查询参数/路径参数的结构和类型
3. 每个端点的成功和错误响应格式
4. 根据代码中的注释和变量名，推断每个字段的业务含义
5. 最后生成一份结构清晰的 API 文档
```

### 方式 C：如果你有 Postman 集合或 curl 记录

Postman 导出的 `.json` 集合文件包含了所有接口的请求信息，是最理想的素材。

**实操步骤：**

1. 在 Postman 中导出你的集合（Collections → Export → 选 JSON 格式）
2. 同样建议先用 [JSON 格式化工具](/tools/json-formatter/) 确认文件无误
3. 上传文件并说：

```
这是我导出的 Postman 集合文件。请帮我：
1. 按模块整理所有接口
2. 提取每个接口的 URL、Method、Headers、Body 参数
3. 根据请求参数推断响应结构
4. 生成一份面向前端/第三方开发者的 API 文档
```

## 二、让 AI 帮你写接口说明和示例

拿到原始接口信息后，AI 生成的文档通常还缺少"人话"——即对业务逻辑的解释、使用场景的说明、常见错误的提示。这些才是用户真正需要的内容。

**实操指令：**

```
基于上面提取的接口信息，请为每个接口补充以下内容：
1. 一句话说明这个接口是做什么的
2. 适用场景（什么情况下调用这个接口）
3. 参数说明表格（字段名 | 类型 | 必填 | 默认值 | 说明）
4. 成功响应示例（JSON 格式）
5. 可能的错误码和错误信息
6. 调用频率限制（如果没有明确说明，标注"待确认"）
```

**效果对比：**

- 没有补充前：`POST /api/v1/users — 创建用户`
- 补充后：`POST /api/v1/users — 创建新用户。用于注册流程或后台管理新增用户。请求体需包含 username（字符串，必填）、email（邮箱格式，必填）、password（最少8位，必填）...`

后者直接就能给用户看，不需要二次加工。

## 三、处理复杂场景：嵌套参数和文件上传

有些接口涉及复杂的嵌套结构（比如多层 JSON）或文件上传（图片、附件），AI 生成时需要特殊处理。

### 嵌套参数

如果你的接口参数有深层嵌套，比如：

```json
{
  "user": {
    "name": "张三",
    "address": {
      "city": "北京",
      "district": "海淀区",
      "detail": "xx路xx号"
    }
  }
}
```

**做法：** 直接把这段示例数据发给 AI，让它基于此生成对应的文档说明：

```
这是一个接口的请求体示例。请根据这个结构，生成完整的参数说明文档，包括每一层的字段名、类型、必填性和说明。
```

### 文件上传

文件上传接口的文档比较特殊，因为涉及 Content-Type 和 FormData。

**做法：** 告诉 AI 你的上传接口路径和文件类型要求：

```
我有一个文件上传接口：POST /api/v1/upload/image
- 参数：file（multipart/form-data，支持 jpg/png，最大 5MB）
- 成功返回：{ "url": "https://...", "id": "xxx" }
- 错误返回：{ "error": "文件大小超出限制" }

请帮我生成这份接口的完整文档，包括前端调用示例（JavaScript fetch + FormData）。
```

## 四、输出格式选择：Markdown、HTML 还是其他

生成好的 API 文档需要发布出去。根据你的需求，可以选择不同的输出格式。

### Markdown（推荐首选）

最简单、兼容性最好的格式。可以直接放在 GitHub/GitLab 仓库里，也可以转为 HTML。

**做法：** 让 AI 直接输出 Markdown 格式：

```
请把以上所有接口文档输出为标准的 Markdown 格式，要求：
1. 每个接口一个二级标题（##）
2. 参数用表格展示
3. 请求/响应示例用代码块包裹，标注语言类型为 json
4. 添加目录（TOC）在最前面
5. 整体结构清晰，方便后续维护
```

生成的 Markdown 文件可以用 198007.xyz 的 [Markdown 在线预览工具](/tools/markdown-preview/) 快速查看渲染效果，确认排版没有问题后再发布。

### HTML

如果需要直接嵌入网站，可以让 AI 输出 HTML 格式。

```
请把上面的 Markdown 文档转换为带基本样式的 HTML 页面，要求：
1. 使用简洁的现代风格（深色背景或浅色均可）
2. 表格、代码块样式完整
3. 包含响应式布局
4. 输出完整的 HTML 文件
```

### YAML/TOML 配置文档

如果你的接口文档需要作为配置文件的一部分（比如给内部系统使用），可以让 AI 输出结构化格式：

```
请把接口列表输出为 YAML 格式，每个接口包含：path、method、summary、parameters、responses 字段。
```

生成的 YAML 文件可以用 198007.xyz 的 [TOML/YAML 在线转换器](/tools/toml-yaml-converter/) 检查格式是否正确，或者在 TOML 和 YAML 之间互转。

## 五、维护和更新：接口变了怎么办

API 文档最大的痛点不是"写"，而是"改"。接口一更新，文档就要跟着改，很容易漏掉。

**解决方案：建立"代码即文档"的工作流。**

1. **定期同步：** 每周或每次迭代结束后，重新运行一次上面的流程——把最新代码/接口定义丢给 AI，让它生成新版文档
2. **差异对比：** 把新旧两份文档分别保存，用 AI 做对比：

```
我上传了两份 API 文档（旧版和新版）。请帮我找出所有变更点，包括：
1. 新增的接口
2. 删除的接口
3. 参数有变化的接口（列出具体变化）
4. 响应格式有变化的接口
```

3. **版本管理：** 在文档开头标注版本号（如 v1.2），每次更新递增。这样前端或第三方开发者能清楚知道当前用的是哪个版本的接口。

## 避坑指南：AI 生成 API 文档的 3 条红线

**1. 敏感信息必须脱敏。** 如果你的接口定义中包含 API Key、数据库连接字符串等敏感信息，上传前先删掉或用占位符替换。可以用 198007.xyz 的 [文本替换器](/tools/text-replacer/) 批量替换敏感字段。

**2. AI 不会猜业务逻辑。** AI 只能从你提供的代码和注释中提取信息。如果你的代码里没有写业务规则（比如"用户年龄必须大于 18 岁"），AI 也不会知道。重要的业务规则需要在指令中额外说明。

**3. 生成的文档一定要人工复核。** AI 偶尔会编造不存在的参数或错误码。特别是对于付费接口或对外公开接口，务必逐条核对，确保文档和实际行为一致。

## 总结：从"没有文档"到"专业文档"，只需要一次对话

以前写 API 文档，需要学 Swagger、手写每一个参数说明、反复调整格式。现在你只需要：

1. 找到接口定义或代码片段
2. 用格式化工具确认文件无误
3. 丢给 AI，给它明确的指令
4. 选择输出格式，发布

整个过程不到 10 分钟，而且每次更新都只需要重新跑一遍。

今天就可以试试：打开你的项目，找一个接口定义文件，用上面的方法让 AI 生成一份文档。你会发现，**好的 API 文档从来不是写出来的，而是"长"出来的。**
