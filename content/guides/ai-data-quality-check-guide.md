每次做报表之前，你最不想碰的事就是发现：上个月的销售表里有 200 行日期是文本、客户名一半带空格一半不带、还有 37 个重复的单号。等发现的时候，透视表已经拉了一半，全得返工。

数据质量平时没人专门管，因为它不直接产出东西，只在出错的时候被看见。中小团队多是「先不管，等报表不对了再回头查」，但回头查的成本永远比事前查高。

现在这套「给数据做体检」的活，可以让 AI 干初筛——你定好规则，它把不合格的字段、行捞出来，你只看它捞出来的。本文从零讲，一张导出表，三步跑完。

## 一、为什么不能直接让 AI「帮我看看这份数据干不干净」

不先定规则就扔数据给 AI，它给你的是「建议检查日期格式是否统一」这种正确的废话——每条都对，但没一条能直接执行。

数据质量检查的正确顺序是**先把「干净」写成可判断的标准**，再让 AI 去核对。可判断，就是每条规则都有一个非黑即白的答案：

| 类别 | 一条合格规则的样子 | 一条不合格规则的样子 |
|---|---|---|
| 缺失 | 「订单金额」列为空的行 | 「检查是否有缺失值」 |
| 重复 | 按「订单号」去重后行数不变的视为无重复 | 「看看有没有重复的」 |
| 格式 | 日期列全部能转成 YYYY-MM-DD | 「日期格式要对」 |
| 取值 | 「状态」列只允许 已支付/已发货/已取消/已退款 | 「状态要合理」 |
| 逻辑 | 退款金额 ≤ 实付金额 | 「数据要合理」 |

规则越具体，AI 查得越准。下面这套规则可以直接抄，再按你的表改字段名。

## 二、第一步：写一份能给 AI 执行的质量规则表

把表头粘给 AI，让它把「模糊的要求」翻译成上面的具体规则：

> "这是我从 ERP 导出的销售表表头：[粘贴 8-15 个列名]。请帮我定一份数据质量检查规则，分五类：缺失、重复、格式、取值范围、逻辑一致性。每条规则写清：检查哪个字段、具体判断条件、命中了算异常。输出表格，规则要具体到 AI 能逐行核对，不要写'格式要规范'这种空话。"

拿回来自己过一遍。重点改两处：**重复判定按哪几列**（很多表业务上允许部分重复，别按全行判），**取值范围的合法集合**（让 AI 先列出它看到的取值，你圈出哪些允许）。

表里有明显异常想针对性查，比如「为什么有的行金额为 0」，单独加一条逻辑规则，比让 AI 自由发挥强。

## 三、第二步：让 AI 逐条查，输出 JSON 结果

### 数据先落到 CSV

Excel 导出的东西带格式，AI 处理不了。先存成 CSV，用 [CSV 在线查看器](/tools/csv-viewer/) 打开确认列没串行、编码没乱。行数多（上千行以上）别整表粘，先取前 100 行做样本核对规则，跑通再上全量。

### 单条规则的检查提示词

这是核心，建议存下来。一次只查一类，比一次查五类稳：

> "你是数据质量检查员。规则：[粘贴一类规则，如缺失类]。数据（CSV）：[粘贴或上传]。
> 请逐行核对，输出 JSON 数组，每条命中一行：
> ```json
> [
>   {"行号": 12, "规则": "订单金额缺失", "原值": "", "建议处理": "填 0 或标记为待补"}
> ]
> ```
> 要求：行号从第 1 行数据（不含表头）起算；原值必须逐字摘录，不许改写；没问题的行不要凑数。"

三个细节。**第一**，让 AI 带「行号 + 原值」，这样你修的时候知道改哪一格，不用反查。**第二**，强制逐字摘录原值，防 AI 概括。**第三**，明确要求「没问题别凑数」，否则它倾向于报出一堆假阳性吓唬你。

跑完一轮，把 JSON 粘到 [JSON 格式化工具](/tools/json-formatter/) 里理一理，用 [文本差异对比工具](/tools/diff-checker/) 对比两次检查结果（修完再查一遍），看还剩多少条。

### 重复单独用 SQL 查最稳

缺失常规则让 AI 查就行，但**去重最可靠的是 SQL**。把 CSV 丢进 [CSV/SQL 在线分析器](/tools/csv-sql-analyzer/)，直接写：

```sql
SELECT 订单号, COUNT(*) AS cnt
FROM data
GROUP BY 订单号
HAVING COUNT(*) > 1
ORDER BY cnt DESC
LIMIT 50;
```

一行 SQL 把重复单号全列出来，比让 AI 数行数准。它还能顺手跑「按状态统计行数以核对取值范围是否完整」，一次查清。

## 四、第三步：把检查结果变成能执行的修复清单

查到一堆异常没意义，关键是要落地成「怎么修」。让 AI 汇总成一张你明天就能照着干的表：

> "以下是本轮数据体检结果（JSON）：[粘贴]。请生成修复清单：
> 1. 按异常类型分组，每组写清数量、涉及字段、最典型的 3 条示例（逐字摘录）
> 2. 每类给一个可执行动作：'把 X 处理成 Y'，例如'日期列文本统一转成 YYYY-MM-DD'、'订单号去重保留最新'
> 3. 标出必须先人工确认的：取值范围拿不准的、逻辑冲突的
> 禁止写'建议规范数据'这类无法执行的表述。"

落成下面这种表，第二天就能开工：

| 异常类型 | 条数 | 典型示例 | 修复动作 | 需人工确认 |
|---|---|---|---|---|
| 日期为文本 | 214 | "2026/11/04" | 统一转 YYYY-MM-DD | 否 |
| 订单号重复 | 37 | ORD-8823 出现 3 次 | 按时间保留最新 | 是 |
| 状态越界 | 5 | "退！" | 归到 已退款 | 是 |
| 退款>实付 | 2 | 退款 99 / 实付 50 | 找源系统核对 | 是 |

最后一列的「需人工确认」别省——机器改数最容易在取值和逻辑这两类上改错，改错的数比没查的数更危险。

## 五、量大之后：写成可重复跑的脚本

如果这份表每天导出、天天要查，手工喂 AI 太累。让它写个脚本：

> "写一个 Python 脚本：读取 data/ 下的 .csv，按我的规则表（缺失/重复/格式/取值/逻辑）逐条检查，结果写成 findings.jsonl，每条含 行号、规则、原值、建议处理。能指定 --sample N 只查前 N 行；失败的规则记到 log.txt，别整份崩。"

跑一遍要几十秒，每天早上起一份 findings.jsonl，只处理新增的行就行。

等异常攒够几千条、想挖规律——比如「哪类客户最容易产生重复单号」——把 findings.jsonl 灌进 [DuckDB](https://duckdblab.org/zh/) 用 SQL 交叉统计，比在 Excel 里一条条拉快得多，数据也留在本地不外流。

## 六、几个容易踩的坑

**坑一：按全行判重复。** 很多业务允许同一订单分多笔明细，全行去重会把正常数据误删。重复一定按「业务主键」判，先问清哪几列合起来才算一条唯一记录。

**坑二：把 AI 修的数直接覆盖原表。** 永远先复制一份再改，留底。改完拿 diff 对比一遍，确认只动了该动的行。

**坑三：规则一次写太全。** 第一遍只查缺失 + 重复 + 日期格式，占掉 80% 的返工。跑顺了再加取值和逻辑。

**坑四：把假阳性当真问题修。** AI 报出来的一定逐条看原值再动手，尤其「逻辑冲突」那类，机器改错比不算更坑。

## 七、第一周怎么开始

1. **今天**：把现有表的列名整理出来，让 AI 帮你定一份五类规则，你改到能逐行核对为止
2. **明天**：取前 100 行做样本，逐类跑检查提示词，据此修规则
3. **第三天**：上全量，重复和取值那两条改走 SQL，结果汇总成修复清单
4. **周五**：照清单修一轮，复制留底 + diff 核对，把这套流程沉淀成脚本

真正省时间的不是「查出了多少问题」，而是**你第一次在拉透视表之前，就知道这张表能信几分**——报表返工那种事，基本绝迹了。
