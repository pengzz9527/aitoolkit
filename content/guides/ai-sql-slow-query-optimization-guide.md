一条查询平时 0.2 秒，某天数据涨到 500 万行之后变成 40 秒，页面直接超时。你盯着这条 SQL，第一反应是"加个索引"，结果加了三个索引，查询反而更慢了。

慢查询优化最反直觉的地方在于：慢的原因几乎从来不是"SQL 写得不够优雅"，而是执行计划走了错路——全表扫描、索引失效、子查询退化成 N+1。这些都不是"语法问题"，AI 也不会主动提醒你，得你先喂给它执行计划。

这篇教程的核心思路：**别凭感觉调 SQL，先让 AI 读懂 EXPLAIN，再针对性改。** 一套排查流程走下来，慢查询到底卡在哪一步就清清楚楚。

## 一、先分清"慢"的三种根源

拿到一条慢 SQL，先别急着动手，花 10 秒判断它属于哪一类：

| 症状 | 最可能的根源 | 第一步该查什么 |
|---|---|---|
| 数据量大就慢，量小就快 | 缺索引，走了全表扫描 | `EXPLAIN` 看 type 是否为 ALL |
| 加了索引还是慢 | 索引失效（隐式类型转换、函数包裹、前导模糊匹配） | 看 `Extra` 里有没有 Using filesort / Using temporary |
| 查询本身简单但结果集巨大 | 子查询 / JOIN 退化成 N+1 | 数一下子查询被执行的次数 |

90% 的"加了索引没用"，都是因为第二种：你以为加了索引，但写法让数据库根本用不上。下面一步步来。

## 二、第一步：让 AI 帮你读懂 EXPLAIN 输出

不要跳过 EXPLAIN 直接让 AI "帮我优化这条 SQL"——那不喂执行计划，AI 只能给你一堆正确的废话。

操作路径（MySQL 为例）：

1. 在慢查询前面加 `EXPLAIN`，或 `EXPLAIN FORMAT=JSON`，把输出整段复制。
2. 重点看三列：**type**（访问方式，ALL 最差、ref/eq_ref 好）、**key**（实际用了哪个索引，NULL 说明没用上）、**rows**（预估扫描行数）。

把输出喂给 AI，提示词直接抄：

> "这是 MySQL 的 EXPLAIN 输出：[粘贴]。对应 SQL 是：[粘贴]。请逐行解释 type、key、rows、Extra 分别说明了什么，明确指出执行计划中最拖后腿的哪一步，以及为什么。不要给我通用建议，只针对这个计划。"

AI 会告诉你，比如：`type=ALL`、`rows=5200000`、`Extra=Using where`——这就是全表扫描 520 万行，问题定位到了。

## 三、第二步：让 AI 定位"索引失效"的具体原因

确认走了全表扫描或 filesort 后，下一步是找"为什么索引没用上"。这是最容易踩坑的一步。

把**表结构（CREATE TABLE）+ 索引定义 + 那条 SQL** 一起丢给 AI：

> "这是表结构和已有索引：[粘贴]。这条查询：[粘贴]。为什么它没走我期望的索引？请逐条排查：是否发生隐式类型转换、是否用函数包裹了索引列、LIKE 是否前导 %、JOIN 列的排序规则是否一致、WHERE 里是否用了 OR。给出每一条的判定结论。"

AI 会帮你逐条核对。最常见的四个失效原因，你可以直接对照：

- **隐式类型转换**：`varchar` 列拿 `int` 去比，比如 `phone = 13800000000`（没加引号），索引直接废掉。
- **函数包裹索引列**：`WHERE DATE(create_time) = '2026-11-12'` 或 `WHERE UPPER(name) = 'X'`，索引列被函数处理后数据库无法使用索引。
- **前导模糊匹配**：`LIKE '%abc'` 没法用普通 B-tree 索引。
- **JOIN 列 collation 不一致**：两个表用 utf8mb4 但排序规则不同，JOIN 时索引失效。

## 四、第三步：生成可落地的优化方案

定位到原因后，让 AI 出方案，但**方案必须可执行、可验证**，让它给出改后的 SQL + 该加的索引 + 验证方式：

> "基于上面的分析，给出优化方案：1) 该加什么索引（写全 CREATE INDEX 语句）；2) 改写后的 SQL；3) 如何验证优化生效（EXPLAIN 预期看到 type/rows/key 变成什么样）。如果子查询能改写成 JOIN 或 CTE，请给两种写法并对比。"

拿回方案后，**先在测试库跑**，对比改前后的 `EXPLAIN` 输出和实际耗时。别直接在生产库加索引——索引不是越多越好，写操作会变慢，加完记得回看 `EXPLAIN` 确认真的走上了。

## 五、四步验证闭环

优化不是一次性的，建个固定习惯：

1. **改前**：记录 EXPLAIN + 实际耗时（`SET profiling=1` 或 `SELECT BENCHMARK`）。
2. **改后**：重跑 EXPLAIN，确认 type 从 ALL 变成 ref/range，rows 大幅下降。
3. **回归**：确认加了索引后，写操作（INSERT/UPDATE）没有明显变慢。
4. **监控**：把这条慢 SQL 加进慢查询日志（`long_query_time=1`），观察一周是否复发。

## 六、把这套流程固化成你的"慢查询排查清单"

整理成一张随手可查的清单，下次遇到慢查询直接照着走：

1. 先 EXPLAIN，看 type / key / rows / Extra 四列。
2. type=ALL → 缺索引或索引失效，进第 3 步。
3. Extra=Using filesort / Using temporary → 排序或分组列没走索引。
4. 对照四大失效原因（隐式转换、函数包裹、前导 LIKE、collation）逐条查。
5. 让 AI 出"加索引 + 改 SQL + 验证方式"三件套，测试库验证后上生产。

## 配套工具

- 查 CSV 导出的慢查询日志、按耗时排序找 Top N 慢 SQL，用 198007.xyz 的 [CSV/SQL 分析器](/tools/csv-sql-analyzer/)，把日志丢进去直接跑聚合。
- 想看某条慢 SQL 占了日志多少比例、按字段分组统计，配 [CSV 查看器](/tools/csv-viewer/) 快速预览结构。
- 把 EXPLAIN 的 JSON 输出贴到 [JSON 格式化](/tools/json-formatter/) 里展开看嵌套的访问方式，比裸 JSON 好读。
- 需要批量改写或做数据验证时，复杂查询和聚合分析直接去 [duckdblab.org/zh/](https://duckdblab.org/zh/)，浏览器里就能跑 DuckDB 分析大表，不用部署服务器。

---

慢查询优化的本质不是背更多索引规则，而是**养成"先读执行计划再动手"的肌肉记忆**。把 EXPLAIN 喂给 AI 定位、再让它出可验证的方案，这套流程跑下来，你对自己系统里每条慢 SQL 到底卡在哪一步都会有清晰的判断，而不是靠猜。
